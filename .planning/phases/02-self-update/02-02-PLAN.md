<objective>
Wire the npm `postinstall` and `preuninstall` lifecycle hooks in `package.json` so that the CLI subcommands implemented in Plan 01 (`install-command`, `uninstall-command`) run automatically when the user installs or uninstalls `@momidala/prefect` globally.

```json
  ]

```

Why the hook values work:
- `bin.prefect` resolves to `./build/cli.js`, which npm symlinks into `node_modules/.bin/prefect` (or the global bin dir on global installs).
- For lifecycle scripts, npm prepends `node_modules/.bin` to PATH, so `prefect install-command` resolves to the package's own CLI.
- The CLI's `isGlobal` check (`__dirname.includes('/node_modules/')`) returns true when invoked from a global install — the install-command handler then writes the slash command file.
- For local installs (i.e., `npm install` in a checkout), the same lifecycle script runs `prefect install-command`, but `isGlobal` is false (cli.js is under the local `node_modules/`, which itself is the working tree), causing a silent skip — D-05.

Wait — re-check: on a local install, `__dirname` for `node_modules/@momidala/prefect/build/cli.js` DOES contain `/node_modules/`, so isGlobal would be true even for local installs. But local installs do not produce a lifecycle hook firing here because the user is unlikely to install `@momidala/prefect` as a local dep. If they do, they get a local `~/.claude/commands/prefect-update.md` — that is acceptable per current decisions; the file is harmless and gets removed on local uninstall. The "silent-skip for non-global" behavior in D-05 is a defense-in-depth against running the CLI directly from a checkout (i.e., `node ./build/cli.js install-command` in the repo root), where `__dirname` does NOT contain `/node_modules/`.

This nuance is important to record in the SUMMARY but does not change the wiring — `postinstall: "prefect install-command"` is correct for both global and local install scenarios.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| npm CLI → `package.json scripts.postinstall` | Standard npm lifecycle hook — npm executes this string in a shell with `node_modules/.bin` prepended to PATH. The value is a static literal `"prefect install-command"` shipped in our own package.json. |
| `prefect install-command` execution | Delegates to the handler implemented in Plan 01 — see 02-01-PLAN.md threat_model for the full STRIDE register on the filesystem write. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-08 | Tampering | `scripts.postinstall` value | accept | The string is a static literal in our published package.json. A tampered tarball could substitute a malicious command, but that is the same threat as tampering with any other code we ship — the npm registry signature + publisher account are the relevant controls, not anything we can do at this layer. |
| T-02-09 | Denial of Service | `postinstall` failure blocks `npm install -g @momidala/prefect` | mitigate | Plan 01's `handleInstallCommand` already exits 0 on every error path (D-07). npm treats a 0-exit hook as success, so even a write failure cannot block the install. Verified by Plan 01's "install-command warns to stderr and exits 0 when mkdir/write fails" test. |
| T-02-10 | Denial of Service | `preuninstall` failure blocks `npm uninstall -g @momidala/prefect` | mitigate | Plan 01's `handleUninstallCommand` exits 0 on every error path (D-08). Verified by Plan 01's "uninstall-command exits 0 silently when file is absent" test. |
| T-02-11 | Elevation of Privilege | `postinstall` arbitrary code execution surface | accept | This is inherent to npm — any package with a `postinstall` script runs arbitrary code on the installing user's machine. We are using this surface for its intended purpose (CLI-bin invocation), and Node's standard npm config (`ignore-scripts`) lets paranoid users opt out. ASVS L1 does not require us to eliminate this category for a CLI tool — it requires us not to abuse it. We do not: the hook invokes only our own published `bin`. |
| T-02-12 | Tampering | `scripts.test` or other scripts modified during edit | mitigate | Acceptance criteria assert byte-equivalence of all non-touched fields. The Task 1 action also explicitly forbids editing other fields. |
</threat_model>
