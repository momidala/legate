## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Project repo (committed source) → OpenCode agent session | `AGENTS.md` is checked into the repo and auto-loaded into the OpenCode agent's system context when `prefect_run` is called with an explicit `directory`. Anyone with commit access to the repo can change what every prefect agent reads. This is the existing trust boundary; Phase 3 does not change it — it adds content within the existing boundary. |
| Prefect agent (OpenCode LLM) → `checkpoint.md` / `Handoff.md` files in the working directory | Agents write these files at instruction-time. The files live in the project working tree. No new write surface is introduced — agents already have unrestricted `edit` / `write` / `apply_patch` permission per OpenCode config (`~/.config/opencode/opencode.json` has `allow` for all). |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-01 | Tampering | `AGENTS.md` content (the instruction surface) | accept | `AGENTS.md` is checked into the repo and reviewed via PR like any other source file. A malicious change to the checkpoint instructions would be caught in code review the same way a malicious change to `src/handlers.ts` would. Pre-existing trust boundary; not introduced by Phase 3. |
| T-03-02 | Tampering | Calibrated trigger language paraphrased or weakened | mitigate | RESEARCH.md Anti-Patterns explicitly forbids paraphrasing. Task 2 acceptance_criteria asserts the literal substring `if you have been working for a long time, if tracking all state feels difficult, or if the conversation feels crowded` is present byte-for-byte. Any drift fails the verification grep. |
| T-03-03 | Tampering | Stop-instruction sentence dropped or weakened | mitigate | RESEARCH.md Pitfall 3 documents this as a known failure mode. Task 2 acceptance_criteria asserts the literal substring `stop initiating new work in this session. Do not wait for an error.` is present. Any drift fails the verification grep. |
| T-03-04 | Information Disclosure | `checkpoint.md` / `Handoff.md` contents reveal work state | accept | These files are written by the agent in the user's working directory. They contain the same information the agent already knows and would emit in chat. If the working directory is a public repo, the user (not prefect) is responsible for `.gitignore` decisions — RESEARCH.md Open Question 2 defers this to future scope (REQUIREMENTS.md "Future Requirements" already lists it). |
| T-03-05 | Denial of Service | Agent writes `checkpoint.md` to an unintended path (e.g., outside working directory) | mitigate | The AGENTS.md instructions say "in the working directory" — a fixed relative reference. OpenCode's `directory` parameter pins the working directory. Phase 1 finding 1 (VERIFIED) confirms the agent operates within the supplied `directory`. No path traversal vector exists in the instruction. |
| T-03-06 | Spoofing | A different file masquerading as `AGENTS.md` is loaded instead | accept | OpenCode's AGENTS.md search order (Phase 1 Finding 1) walks upward from `directory`, falling back to `~/.config/opencode/AGENTS.md`. A spoofing scenario would require a malicious file higher in the tree than the project's `AGENTS.md` — which would already compromise every project under that directory. Pre-existing risk; not introduced by Phase 3. |
| T-03-07 | Repudiation | Agent writes `checkpoint.md` without timestamps or session linkage | accept | The schema (Phase 1 canonical template) does not require timestamps. Adding them is a Future Requirement (REQUIREMENTS.md "Optional: checkpoint.md committed automatically with a standard message" — git provides the timestamp). Accepting because the file is a working-document for context handoff, not an audit log. |
| T-03-08 | Elevation of Privilege | The instruction grants the agent any new capability | mitigate | The instruction tells the agent to call `edit` / `write` / `apply_patch` — tools it already has. No new tool grant, no new permission scope. The instruction is purely directive over existing capabilities. |
</threat_model>
